---
title: "Digital Certificate Registration"
openapi: "openapi/vault.json POST /credentials/certificate"
api: "POST https://crawler.prod.judit.io/credentials/certificate"
description: "Register an A1 digital certificate (.pfx / .p12) as a credential in the vault. This is the only route that accepts certificate upload."
icon: "certificate"
---

<Warning>
The certificate **cannot** be sent through the `POST /credentials` route: there, the `file_base64` field is silently ignored and certificate fields inside `custom_data` are rejected with `CERTIFICATE_FIELDS_NOT_ALLOWED`.
</Warning>

<Info>
The certificate is always registered as the **wildcard credential** (`*`) of the given `customer_key`: it applies to every system that has no specific credential for that `customer_key`. A `system_name` sent to this route is silently ignored.
</Info>

<Note>
This route only accepts `file_base64`, `password` and `customer_key`. Other fields, such as `system_name`, `totp_secret` or `custom_data`, are **silently ignored**. If the court also asks for an authenticator app code, [contact Judit support](/en/resource/support).
</Note>

<ParamField body="file_base64" type="string" required>
Content of the `.pfx` / `.p12` (PKCS#12) file converted to Base64, on a **single line**, with no breaks. File must be at most 64 KB.
</ParamField>

<ParamField body="password" type="string" required>
Password of the `.pfx` file. Not the court portal password.
</ParamField>

<ParamField body="customer_key" type="string">
Credential identifier defined by you. If omitted, the default value `*` is used.
</ParamField>

<RequestExample>
```bash cURL
curl --location 'https://crawler.prod.judit.io/credentials/certificate' \
--header 'api-key: <api-key>' \
--header 'Content-Type: application/json' \
--data '{
  "customer_key": "lawyer_01",
  "file_base64": "<pfx-content-in-base64>",
  "password": "<pfx-file-password>"
}'
```
</RequestExample>

<ResponseExample>
```json
{
	"message": "CERTIFICATE_CREATED",
	"customer_key": "lawyer_01",
	"subject_cn": "HOLDER NAME:12345678909",
	"not_after": "2027-01-01T00:00:00.000Z",
	"uploaded_at": "2026-07-31T17:00:00.000Z"
}
```
</ResponseExample>

**If a certificate for the same holder already exists for that `customer_key`, the message will be `CERTIFICATE_UPDATED` and the previous certificate is discarded.**

<Accordion title="Possible errors">
Errors come in the format `{ "error": { "name", "message", "data": ["<CODE>"] } }`.

| Code | HTTP | When it happens |
| :--- | :--- | :--- |
| Validation error | 400 | `file_base64` or `password` is missing |
| `PFX_MALFORMED` | 400 | Invalid Base64 or corrupted PFX file |
| `PFX_PASSWORD_INVALID` | 400 | Wrong file password |
| `PFX_NO_PRIVATE_KEY` | 400 | File has no private key |
| `PFX_NO_CERTIFICATE` | 400 | File has no certificate |
| `PFX_EXPIRED` | 400 | Certificate expired |
| `PFX_NOT_YET_VALID` | 400 | Certificate not valid yet |
| `PFX_TOO_LARGE` | 400 | File larger than 64 KB |
| `CERTIFICATE_HOLDER_MISMATCH` | 409 | A certificate from another holder (CPF/CN) is already registered for this `customer_key` |
| `CREDENTIAL_TYPE_CONFLICT` | 409 | A wildcard (`*`) username/password credential already exists for this `customer_key` |
</Accordion>

Full guide, including converting the file to Base64 and the Postman walkthrough: [Credentials Vault — digital certificate](/en/essentials/cofre-de-credenciais#registering-a-credential-with-a-digital-certificate-a1).

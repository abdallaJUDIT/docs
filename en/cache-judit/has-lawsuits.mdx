The **Has Lawsuits? Synchronous Query** returns, in milliseconds, a boolean indicating whether a CPF, CNPJ, OAB or Name has **any lawsuit** in the Judit datalake. It's the lightest, cheapest path for binary gates — KYC, lead qualification, alerting and routing.

> 🤖 Endpoint: `POST https://lawsuits.production.judit.io/lawsuits` with `pagination.page_size: 1`. The response includes the top-level boolean `has_lawsuits`. Use `page_size: 1` to minimize payload — the goal here is just to know **if it exists**, not to bring the full list.

<EndpointBadges auth billing="billable" flow="sync" />

## When to use

<CardGroup cols={2}>
  <Card title="KYC gate" icon="shield-halved">
    During onboarding, decide whether to run a full diligence only when `has_lawsuits = true`.
  </Card>
  <Card title="Lead qualification" icon="filter">
    Auto-tag leads as "with legal risk" before deepening the analysis.
  </Card>
  <Card title="Routing & alerts" icon="route">
    Route to specific flows (risk desk, advanced compliance) only people who have lawsuits.
  </Card>
  <Card title="Status badges" icon="bolt">
    Paint a "has-lawsuits / clean" badge on CRM/ERP without bringing the full list.
  </Card>
</CardGroup>

<Note>
For the **count** of lawsuits, use [`POST /lawsuits/count`](/en/cache-judit/count). For the full list of lawsuits, use [`POST /lawsuits` (Hot Storage)](/en/cache-judit/hotstorage).
</Note>

## Step 1: Create the query (POST)

`POST https://lawsuits.production.judit.io/lawsuits`

### Payload parameters

| Parameter | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `search.search_type` | string | **Yes** | `cpf`, `cnpj`, `oab`, `name` or `rji`. |
| `search.search_key` | string | **Yes** | Document or name to query. |
| `search.response_type` | string | **Yes** | Use `"lawsuits"` for this route. |
| `search_params.pagination.page_size` | number | Recommended | Use `1` to minimize traffic — we only need `has_lawsuits`. |
| `search_params.filter` | object | No | Same filters as [Hot Storage](/en/cache-judit/hotstorage) (side, tribunals, dates, amount, classes, subjects, etc.). |

## Step 2: Read the response

The response is a synchronous JSON. The relevant field for this use case is `has_lawsuits`.

```json Response
{
    "has_lawsuits": true,
    "request_id": "87d9f7bf-0071-41ee-a721-e6e1b4082bc9",
    "lawsuits": [
        {
            "code": "0000000-00.0000.0.00.0000",
            "...": "..."
        }
    ]
}
```

| Field | Type | Description |
| :--- | :--- | :--- |
| `has_lawsuits` | boolean | `true` if there is at least one lawsuit in the datalake; `false` otherwise. |
| `request_id` | string | UUID of the query — useful for auditing. |
| `lawsuits` | array | List of lawsuits (empty or with 1 item, if `page_size: 1`). |

<Note>
If you only want the boolean and don't need the `lawsuits` array, we still recommend `page_size: 1` (the API always returns the full structure, but with a minimized array). For just the count (e.g. "has 12 lawsuits"), use [`POST /lawsuits/count`](/en/cache-judit/count).
</Note>

## Patterns and tips

<AccordionGroup>
  <Accordion title="Combine with filters for contextual gates">
    Want to know if the person has an **active labor lawsuit on the defendant side in the last 5 years**? Combine `tribunals.keys`, `side`, `distribution_date_gte`. All in a single synchronous call.
  </Accordion>

  <Accordion title="Handling homonyms in name searches">
    `name` searches may return homonym matches. For common names (e.g. "John Smith"), confirm via CPF before blocking the user. Judit returns heuristics (`possible_homonym`, `potential_homonym`) in the list — if you only need the boolean, complement the gate with another document check.
  </Accordion>

  <Accordion title="Cost vs. full list">
    This route is billed as a standard synchronous query. If you're already going to fetch the full list right after, skip this step and use [Hot Storage](/en/cache-judit/hotstorage) directly.
  </Accordion>

  <Accordion title="Cache (TTL)">
    The result can be cached client-side following `cache_ttl_in_days`. For critical KYC flows, consider a shorter TTL (1 day) or force a refresh via [`POST /requests`](/en/requests/requests) with `on_demand: true`.
  </Accordion>
</AccordionGroup>

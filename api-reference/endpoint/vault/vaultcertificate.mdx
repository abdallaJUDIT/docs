---
title: "Cadastro de Certificado Digital"
openapi: "openapi/vault.json POST /credentials/certificate"
api: "POST https://crawler.prod.judit.io/credentials/certificate"
description: "Cadastre um certificado digital A1 (.pfx / .p12) como credencial no Cofre. Esta é a única rota que aceita upload de certificado."
icon: "certificate"
---

<Warning>
O certificado **não** pode ser enviado pela rota `POST /credentials`: lá, o campo `file_base64` é ignorado sem erro e campos de certificado dentro de `custom_data` são recusados com `CERTIFICATE_FIELDS_NOT_ALLOWED`.
</Warning>

<Info>
O certificado é sempre cadastrado como **credencial coringa** (`*`) da `customer_key` informada: vale para todos os sistemas que não têm credencial específica nessa `customer_key`. Um `system_name` enviado nesta rota é ignorado sem erro.
</Info>

<Note>
Esta rota aceita apenas `file_base64`, `password` e `customer_key`. Outros campos, como `system_name`, `totp_secret` ou `custom_data`, são **ignorados sem erro**. Se o tribunal também pedir o código do aplicativo autenticador, [entre em contato com o suporte da Judit](/resource/support).
</Note>

<ParamField body="file_base64" type="string" required>
Conteúdo do arquivo `.pfx` / `.p12` (PKCS#12) convertido para Base64, em **uma única linha**, sem quebras. Arquivo com no máximo 64 KB.
</ParamField>

<ParamField body="password" type="string" required>
Senha do arquivo `.pfx`. Não é a senha do portal do tribunal.
</ParamField>

<ParamField body="customer_key" type="string">
Identificador da credencial definido por você. Se omitido, é usado o valor padrão `*`.
</ParamField>

<RequestExample>
```bash cURL
curl --location 'https://crawler.prod.judit.io/credentials/certificate' \
--header 'api-key: <api-key>' \
--header 'Content-Type: application/json' \
--data '{
  "customer_key": "advogado_01",
  "file_base64": "<conteudo-do-pfx-em-base64>",
  "password": "<senha-do-arquivo-pfx>"
}'
```
</RequestExample>

<ResponseExample>
```json
{
	"message": "CERTIFICATE_CREATED",
	"customer_key": "advogado_01",
	"subject_cn": "NOME DO TITULAR:12345678909",
	"not_after": "2027-01-01T00:00:00.000Z",
	"uploaded_at": "2026-07-31T17:00:00.000Z"
}
```
</ResponseExample>

**Se já existir um certificado do mesmo titular nessa `customer_key`, a mensagem será `CERTIFICATE_UPDATED` e o certificado anterior é descartado.**

<Accordion title="Erros possíveis">
Os erros vêm no formato `{ "error": { "name", "message", "data": ["<CÓDIGO>"] } }`.

| Código | HTTP | Quando acontece |
| :--- | :--- | :--- |
| Erro de validação | 400 | `file_base64` ou `password` ausente |
| `PFX_MALFORMED` | 400 | Base64 inválido ou arquivo PFX corrompido |
| `PFX_PASSWORD_INVALID` | 400 | Senha do arquivo incorreta |
| `PFX_NO_PRIVATE_KEY` | 400 | Arquivo sem chave privada |
| `PFX_NO_CERTIFICATE` | 400 | Arquivo sem certificado |
| `PFX_EXPIRED` | 400 | Certificado vencido |
| `PFX_NOT_YET_VALID` | 400 | Certificado ainda não vigente |
| `PFX_TOO_LARGE` | 400 | Arquivo maior que 64 KB |
| `CERTIFICATE_HOLDER_MISMATCH` | 409 | Já existe certificado de outro titular (CPF/CN) nessa `customer_key` |
| `CREDENTIAL_TYPE_CONFLICT` | 409 | Já existe uma credencial coringa (`*`) de usuário e senha nessa `customer_key` |
</Accordion>

Guia completo, com conversão do arquivo para Base64 e passo a passo no Postman: [Cofre de Credenciais — certificado digital](/essentials/cofre-de-credenciais#cadastro-de-credencial-com-certificado-digital-a1).
